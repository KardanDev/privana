# KAR-142 — Brand surfaces and CMS replacement behavior

Source audit, November 7, 2026. This is an inventory of current behavior and asset adoption work, not a claim that the new identity is already installed. The [asset kit](asset-guide.md) follows KAR-141's selected direction. Later groups require owner authorization; this story starts none of them.

| Surface / source | Current behavior | Adoption / review requirement |
| --- | --- | --- |
| [Shared Brand](../../../apps/web/src/shared/components/brand.tsx), used by topbar/sidebar, auth and owner shell | Published `brand.logoUrl` uses a 36px image. Empty URL uses an older inline P; the name remains live CMS text with a purple period. Compact/hide behavior changes with the shell. No failed-remote-image fallback exists in this component. | KAR-148: adopt approved default mark; keep accessible product link, custom name and square custom image precedence. Do not hardcode the outlined “privana” when the owner changes the name. Treat an unreachable custom image explicitly. |
| [CMS identity fields](../../../apps/web/src/domains/admin/cms/cms-brand-fields.tsx), [preview](../../../apps/web/src/domains/admin/cms/cms-preview.tsx) | Name/tagline/logo URL/accent are editable. Logo accepts HTTPS or a safe local absolute path, not a file upload. Preview shows the draft URL in a 40px slot; an empty draft currently shows no fallback mark. | KAR-146/168: explain square-image preference, show the same approved default/override appearance in preview and public shell, and preserve draft-versus-published distinction. `/brand/mark.svg` is an available square source after deployment; do not write it to saved config here. |
| [Config contract](../../../packages/api/src/contracts/platform.ts), [safe URL validator](../../../packages/api/src/contracts/is-safe-platform-url.ts) | One shared logo URL and six-digit accent. Accent requires at least 4.5:1 against white. Safe URLs reject credentials, protocol-relative links and unsafe decoded characters; they do not prove the file exists or is square. | Keep this validation and saved overrides. The fixed-color asset cannot automatically follow CMS accents through an external image. Later theme parity must verify generated semantic states, not assume primary contrast proves all states. |
| [Publish](../../../packages/api/src/domains/admin/cms/publish.ts), [published config](../../../packages/api/src/domains/platform/read-published-config.ts), [loader](../../../apps/web/src/shared/platform/load-platform.ts) | Draft/save/publish are distinct. Publish uses expected version; shell reads published config. Loader falls back to default config on read failure. | Keep existing optimistic/concurrency/error contracts. Do not publish assets or rewrite CMS documents automatically from builds. These are source observations, not a newly exercised CMS journey. |
| [Page metadata](../../../apps/web/src/shared/platform/platform-metadata.ts) | Application name/title/description use config. Favicon is the same custom logo URL or old `/favicon/favicon.svg`; no social image or Apple icon is configured here. | KAR-153: wire reviewed default favicon, Apple and social exports; retain truthful customized name. A default static “privana” social image cannot silently represent a differently named platform. |
| [Dynamic app manifest](../../../apps/web/src/app/manifest.ts) | Uses config name/accent and one `any` icon from shared logo URL or old favicon; no explicit PNG sizes/maskable entry. | KAR-153: choose supplied 192/512 `any` and dedicated maskable assets when using the default identity; preserve actual custom-logo behavior until replacement settings exist. Verify generated manifest and real install/crop behavior. |
| [Legacy static manifest](../../../apps/web/public/favicon/site.webmanifest), public favicon assets | Separate older icon family remains. Static manifest has root icon paths although its images are in `/favicon/`; the dynamic manifest is the current application source. | KAR-153: reconcile/remove stale references deliberately during adoption. Do not claim new `/brand/` files repair existing metadata merely by being present. |
| [Auth email renderer](../../../packages/auth/src/email/render-auth-email.ts), [offline fallback](../../../apps/web/public/offline.html) | Auth email uses escaped dynamic brand text, Arial and fixed purple styling; no logo image. Offline page is a separate English document without the product identity. | KAR-153: align existing email/fallback branding and pt-BR as scoped there; preserve deliverability, reset/verification URL contracts and secret-free evidence. No email is sent or template changed in this asset story. |
| [Avatar](../../../apps/web/src/shared/components/avatar.tsx), [image state](../../../apps/web/src/shared/components/use-avatar-image.ts) | Existing avatar falls back to name initials on absent/failed image. Creator covers/media remain creator-owned content. | Supplied neutral avatar/cover are optional reviewed defaults, not forced replacements. Preserve initials/custom media behavior and never turn a platform placeholder into a verification badge. |

The current CMS has **one** logo URL. Separate light/dark wordmarks, favicon, social image, app icons, font selection and fallback-asset uploads are not existing controls. The asset kit prepares those variants; it does not imply a new no-code media manager exists. Keep the approved base identity usable with existing settings and scope any expanded CMS capability separately.
