# Member experience: social product redesign

> Historical design proposal. The current implementation and November 6 browser evidence are documented in [verification.md](verification.md) and [optimistic-updates.md](optimistic-updates.md). Findings below describe the earlier design, not the current screens.

Read-only audit and proposed implementation boundaries. No application code changed. The target is a creator social network with a subscription relationship, using Privana's royal purple identity. This proposal uses the current repository and the owner's stated references; it does not claim a current screen-by-screen comparison of OnlyFans, Fansly or Fanvue.

## Findings in the current implementation

- `apps/web/src/domains/discovery/discovery-page.tsx:60` — the home screen begins with a large promotional hero; its 58px headline, serif emphasis and decorative monogram delay actual creator content. Another promotional section follows the creator list at line 182.
- `apps/web/src/shared/layout/app-shell.tsx:32` — a 236px sidebar, large outer padding and 1440px content maximum serve every route. The social stream, profile and inbox need different widths and padding.
- `apps/web/src/shared/layout/topbar.tsx:12` — the 78px global bar repeats a brand slogan and a search-shaped link that navigates home. It occupies space without exposing the current route's actual task.
- `apps/web/src/domains/feed/feed-page.tsx:28` — oversized page headings and marketing copy precede the stream; the actual feed already has useful typed queries, pagination and working engagement controls.
- `apps/web/src/domains/posts/post-card.tsx:52` — every post is a large rounded, bordered card with internal padding; repeated stacked containers dilute the visual importance of the media and author. Report controls always occupy their own row.
- `apps/web/src/domains/creators/creator-card.tsx:13` — tall editorial photo tiles, floating arrows and a separate avatar/name/bio/price stack make discovery feel like a portfolio directory.
- `apps/web/src/domains/creators/creator-page.tsx:48` — the cover/avatar relationship is a good base. The nested card treatment and promotional membership panel should become an integrated social profile.
- `apps/web/src/domains/messages/conversation-panel.tsx:94` — a fixed 620px conversation height does not adapt to the mobile viewport and keyboard. The existing participant authorization and older-history pagination should be retained.
- `apps/web/src/domains/discovery/discovery-page.tsx:30` — search/category state exists only in React; navigation back to discovery loses the shareable search context. Categories are hardcoded at line 20.
- `apps/web/src/domains/creators/creator-card.tsx:17` — hover image scaling/arrow rotation have no reduced-motion variant. The redesign should also preserve visible keyboard focus and label icon-only navigation, following the [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md).

## Proposed CMS contract needs — names are provisional

Coordinate these with the root agent's DTO before implementation:

- `brand`: product name, short name, logo/light-dark assets, favicon, support identity.
- `theme`: validated primary/accent colors, surface palette, light/dark/system choice, approved sans typography preset, constrained density/radius values. The social default is 8–12px utility panels, mostly unrounded stream content, full-round avatars, restrained pill buttons; no giant radius on every surface.
- `navigation`: known destination IDs, editable labels, order and visibility for desktop/mobile/account menus. Each configured destination resolves to a valid product route with an accessible name; icon-only rail links retain tooltips and screen-reader text.
- `pages`: titles, short descriptions, empty-state copy and action labels keyed by known page/component IDs, including authentication, feed, explore, saved, profile, inbox, notifications, memberships and settings. Error handling and payment/access status remain functional states rather than editable claims.
- `discovery`: stable category values + labels, suggested-creator module visibility/title and curated creator IDs if wanted. Curated IDs must resolve to currently visible creators through the server.
- `modules`: typed enabled/order/placement settings for suggestions, announcement, membership panel and footer; published announcement text and optional validated internal/HTTPS action. Avoid arbitrary HTML/CSS/script blocks so a saved setting remains predictable across desktop and mobile.
- `membership`: panel title, launch-interest label and explanation; current checkout availability is server-owned. CMS cannot turn interest into an active subscription or imply payment success.
- `legal`: published policy/support labels, destinations and optional page bodies; SEO metadata and share images should derive from the same public brand settings.
- `revision`: published revision ID/timestamp, with separate admin draft state. Root loads one public settings snapshot and supplies it through the shared shell/provider; member components do not independently fetch global settings.

## Component ownership and sequence

Root: settings DTO/provider, theme tokens, navigation and shell variants, admin CMS. Member scope: home/explore composition, compact creator cards/profile, post stream composition, contextual right-rail modules, inbox/notifications/settings styling. Auth owner: auth layout/copy consumption from the same settings snapshot.

Sequence: agree public settings DTO → implement shell/theme → recompose home/post stream → implement explore and creator profile → align utility screens → connect every configurable slot → desktop/mobile/keyboard review. Reuse the existing typed product API, persisted interactions, authorization gates and honest loading/error/empty states throughout.

Acceptance checks: the first mobile home viewport shows a contextual header/tabs and real post content or an actionable empty state; no marketing hero or serif slogan; navigation reaches every existing member route; scroll position/search/tab state survive expected navigation; changing/publishing the CMS brand/theme/copy updates all applicable surfaces; unpublished drafts remain invisible; locked MP4/media remain absent from unauthorized markup; all configured navigation/actions remain keyboard usable.
